# x86_64 AtomVM vs BEAM — baseline — 2026-09-18

First full three-workload measurement on the **x86_64** host since 2026-06-17.
The optimisation campaign of July–September ran on aarch64 (M4 Mac mini) and
arm32, so this run answers one question: how much of that work carried over.

Ratios are `BEAM time / AtomVM time` (ESTONE: `AtomVM estones / BEAM estones`).
**Greater than 1 means AtomVM wins.**

## Summary

| benchmark | x86_64 today | aarch64 reference | x86_64, 2026-06-17 |
|---|---:|---:|---:|
| `erlc`, one VM per application (throughput) | **0.781x** | 1.007x (09-06) | — |
| `erlc`, one VM per file (what a user waits for) | **1.651x** | 1.861x (09-06) | 0.85x |
| ESTONE common subset (score) | **0.893x** | 0.907x (09-06), 0.988x (09-13) | ~0.66x (July) |
| benchmark app, 10 tests excluding `estone_test` | **1.097x** | 1.282x (09-06) | — |

The x86_64 port improved a great deal since June (per-file `erlc` 0.85x ->
1.65x), but it sits **below the aarch64 position on every workload**, and the
one workload measuring pure compile throughput — `erlc` in batch mode — is the
outlier: **AtomVM is 28% slower than BEAM here, while aarch64 reached parity.**

Cross-host ratios are not a controlled comparison: BEAM's own x86_64 JIT is its
most mature backend, so part of this gap is BEAM being stronger here rather
than AtomVM being weaker.  The per-component evidence below nevertheless points
at specific missing x86_64 codegen.

### ESTONE runner caveat

The aarch64 reports used a local `estone` module that is not in either
repository.  It was reconstructed here (scratch `estone.erl`, calling the

## Where the x86_64 backend is behind — static evidence

`jit.erl` probes each backend for optional capabilities with
`erlang:function_exported/3` and falls back to a longer generic sequence when
one is absent.  Capabilities the x86_64 backend does **not** export while
aarch64 or arm32 does:

`addsub_smallint_fused`, `and_to_native_register`, `can_test_in_place`,
`copy_array_elements`, `extract_bits`, `get_array_elements_pair`,
`move_array_elements_pair`, `move_to_vm_registers_pair`, `or_shifted_arith`,
`read_shrink_probe_mismatch`, `rewind_stream`, `set_branch_hints`,
`take_overflows`.

The first one lines up exactly with the worst ESTONE component:
`addsub_smallint_fused/4` collapses the two tag tests and the overflow test of
the `+`/`-` fast path into a **single** branch.  aarch64 and arm32 implement
it; x86_64 falls back to `op_gc_bif2_addsub_hot_split`, which emits **three**
separate branches to the cold arm plus an unaliasing copy.  x86_64 can do the
fused form (`test`/`lea`/`add` set flags, and `jo` catches overflow), so this
is a missing implementation, not an ISA limit.

Several others are genuinely ARM-shaped (`or_shifted_arith`, `extract_bits` =
`ubfx`, the `ldp`/`stp` pair moves) and need an x86_64-native equivalent
rather than a port; `can_test_in_place` and `set_branch_hints` look
straightforwardly available on x86_64.

This list is a **hypothesis list from static reading**, not a measurement.  Each
entry must be A/B'd on one tree with a minimal diff, rebuilt in place — the
cross-build attribution trap documented in
[`BENCHMARK_STATUS_2026-09-06.md`](BENCHMARK_STATUS_2026-09-06.md) applies here
too.

# Round 2 — three x86_64 changes, same day

Measured after the baseline above, same host, same method, same corpus.
Ratios are still `BEAM / AtomVM` (ESTONE: score ratio); >1 means AtomVM wins.
ESTONE and the app suite are re-measured on the final tree (ESTONE 1.003x,
bootstrap CI 0.995–1.023, 31 rounds); the two `erlc` figures were taken one
change earlier, before the typed-range half of change 1, which can only help.

| benchmark | baseline | after | aarch64 reference |
|---|---:|---:|---:|
| ESTONE common subset (score) | 0.893x | **1.003x** | 0.907–0.988x |
| benchmark app, 10 tests excl. `estone_test` | 1.097x | **1.139x** | 1.282x |
| `erlc` batch (throughput) | 0.781x | **0.804x** | 1.007x |
| `erlc` per-file | 1.651x | **1.680x** | 1.861x |

`erlc` moved least, and the profile says why: on this corpus AtomVM spends
~35% of its time in map operations, ~29% in GC copying (`memmove` +
`memory_shallow_copy_term_impl`) and ~14% in comparisons, with **no measurable
time in generated code**.  The GC is reached almost entirely through
`jit_memory_ensure_free_with_roots_pin` (allocating opcodes), not through
`test_heap`, so the corridor check helps only at the margin here.  Closing the
`erlc` gap is a C-runtime problem — map-update allocation and the copying
collector — not a codegen one.  Per-application `erlc` batch ratios now:
compiler 0.792x, stdlib 0.774x, kernel 0.866x, sasl 0.921x, crypto 1.228x;
per-file 1.552x / 1.423x / 2.353x / 2.499x / 1.461x.

## 1. `div`/`rem` by a power-of-two literal, dividend of unknown sign

`estone`'s `int_arith` was **0.39x**, half the entire ESTONE deficit.  It is
not the arithmetic: attributing it by deleting one operator class at a time
from `do_arith2` showed the two `div 2` per call cost AtomVM 167 ms of 339 ms
while they cost BEAM 20 ms of 148 ms.  A 64-bit `idiv` is tens of cycles on
this CPU, and the JIT emitted one because the dividend's sign was unknown: the
existing power-of-two shift path requires a type-proven **non-negative**
range, since an arithmetic shift floors while Erlang's `div` truncates toward
zero.

Fix (`jit.erl`, all backends): strength-reduce the runtime small-integer
fast path with the standard bias.

    Bias = (V bsr (Bits-1)) bsr-logical (Bits-Shift)   % 2^Shift-1 iff V < 0
    div:  (V + Bias) bsr Shift
    rem:  V - ((V + Bias) band bnot (2^Shift-1))

Since a power-of-two divisor needs no hardware divide at all, the fast path is
now also taken on backends whose `supports_div` is false (arm32).  The same
sequence replaced the hardware divide for a **type-proven** dividend whose
range spans negatives, which previously emitted `idiv`/`sdiv`.

Effect: `int_arith` **0.39x -> 0.76x**; the isolated micro went 8,586 us ->
4,132 us per run (2.08x); `div 2` in the operator micro 2.35 ns -> 1.48 ns.

## 2. `/=` inlines the same fast path `==` does

`op_is_not_equal` always called the C comparator, while `==`, `<`, `>=`,
`=:=` and `=/=` all had the both-small-integer inline path.  Mirrored it.

No measurable effect on these four benchmarks — the OTP compiler rewrites the
`/=` in estone's `pat_loop3` to `is_ne_exact` with a typed operand, so the
opcode never appears there.  Kept because it is a real asymmetry, one that
costs a call per guard in code that does reach it.

## 3. The `test_heap` corridor check, inlined on x86_64 (the big one)

Profiling estone's `pattern` micro alone put **`jit_test_heap_pin` at the top**
(233 of ~1,500 samples), ahead of the GC itself.  aarch64 already inlines the
free-space corridor check; x86_64 opted out on a 2026-06-11 measurement that
found the call cheaper than the inline test.

That measurement predates pinned `heap_ptr`/`e` registers.  With them,
`read_avail_heap_memory` is two register instructions and no memory access, so
the corridor check is `mov`/`sub`/`sub`/`cmp` and one predicted branch.
Implementing `read_shrink_probe_mismatch/1` for x86_64 (six instructions:
`heap.root->next | (heap_end ^ shrink_probe_heap_end)`) turns the shared
`op_test_heap` fast path on for the backend.

Controlled A/B, one tree, the export line as the only difference, both sides
rebuilt in place (VM + `atomvmlib` + workload AVM):

- ESTONE score **+10.7%** (887,314 -> 982,215, bootstrap CI 1.096–1.109)
- benchmark app aggregate **+3.1%** (CI 1.016–1.054): `pi_test` +15.5%,
  `sudoku_puzzle` +5.0%, `list_test` +3.1%, `estone_test` +3.2%;
  `bigint_test` −4.5% and `pingpong` −1.5% are the only losses.

The June note's worst case (pingpong +10-25%) did not reproduce.

## What was measured and rejected

- **`addsub_smallint_fused` for x86_64** (the capability aarch64 and arm32
  have and x86_64 does not).  Not built: the x86_64 split form is already 8
  instructions with two never-taken branches, the fused form needs `seto` plus
  an extra temp and comes out longer.  The operator micro puts the marginal
  cost of an untyped `+` at 0.25 ns against BEAM's ~0, i.e. the add itself is
  not where `int_arith` loses; the call shape is (`callonly` 1.62x).
- **Value-context comparison BIFs** (`X = A < B`, 2.29x on ints, 3.19x on
  floats) have no inline path, but they do not appear in the erlc profile and
  estone's guards compile to the branch form, which is already 1.30x.  Parked
  with the measurement.
- Float **guard** comparisons are 5.05x (`float_lt_guard` 17.11 ns vs 3.39 ns).
  The compare fast path inlines small integers only; floats always call the C
  comparator.  Not attempted here, but it is the clearest remaining
  single-opcode gap and it is shared with aarch64.
