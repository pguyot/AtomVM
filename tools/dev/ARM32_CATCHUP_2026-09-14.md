# Closing the arm32 gap: what shipped, what it bought, what is left — 2026-09-14

Follow-on to [ARM32_VS_GRISP_2026-09-13.md](ARM32_VS_GRISP_2026-09-13.md),
which measured AtomVM at 0.73x of GRiSP's `arm32-jit/OTP-29.0.6` BeamAsm on
ESTONE and attributed the gap. This one implements against that attribution
and re-measures. Same host (`mx2.local`, Raspberry Pi 2, Cortex-A7 at 900 MHz,
`performance` governor), same workload, same interleaved method.

## Result

Five interleaved ESTONE rounds per build, medians. `head` is `w30/jit-edge` at
0cfb5ace5.

**This is a trade, not a free win, and the table should be read with the
per-round spreads in hand.** `fcalls` has a spread of 1.01 in every build, so
its 6% is real. `msgp_medium` has a spread of 1.27-1.33 in every AtomVM build
(the documented bimodality) and its 1.255 is mostly which cluster each build
drew; comparing minima gives 1.034. `msgp` (spread 1.07-1.10) does separate
cleanly -- head's worst round beats the new build's best -- so its ~10% is
real, and so is `generic`'s 4-6%. Those are the micros that mostly tail-call
primitives, which is exactly where the reduction-count flush was added, and
the regression is already present in the pinning-only build.

## What shipped

**The reduction count in a register** (`c2040aaf2`). Every reduction charge --
the back edge of every loop, every call -- was `ldr`/`subs`/`str` through
`jit_state->remaining_reductions` where aarch64 spends one `subs` on its pinned
x24. It now lives in r11, seeded by the dispatch loop and flushed only where C
can read it (before tail-calling a primitive, and before the `*_direct`
wrappers whose `jit_direct_continuation` check reads it from memory), never
after a call -- the primitive may have zeroed it itself to force a reschedule.

r11 is the ARM frame pointer. It is listed as an asm **clobber** and never
bound to a register variable: a variable makes the compiler materialise its
value into r11 around the asm, which is the shape that once cost us a dropped
heap-pointer bump. A clobber is honoured or rejected at compile time, so a
`-fno-omit-frame-pointer` build fails loudly instead of miscompiling.

**ldrd/strd** (`1365b612d`, `1691f0f52`). Three places moved two adjacent words
with two loads and two stores, because `cp_t` spans two slots below 64 bits and
a cons has two cells: the frame push in `allocate_frame_fast`, the frame pop in
the `call_ext` fast path, and `OP_GET_LIST`. All three pairs are adjacent and
doubleword-aligned. For `OP_GET_LIST` the cell order lands the head in the odd
register and the tail in the even one, so the two end up in distinct registers
and a following read of either elides the reload -- which is the point of
aarch64's `get_list_head_tail`, now exported by arm32 as well. Each keeps the
two-instruction-per-word form for when no even/odd pair is free or the offset
overflows ldrd's 8-bit immediate (a frame deeper than 62 slots).

**ets** (`8232ea55e`, `258452347`, `620808008`, `6c8d25f13`), which was 4.16x
on arm32 and 3.97x on aarch64 -- equally bad on both, so not an arm32 problem
at all. `ets:match/2` and `ets:match_delete/2` build a `select/2` match spec,
and `select/2` copied the **entire table** with `tab2list/1` and then
interpreted the spec over every object, even when the caller had written the
key into the pattern. Splitting the micro by operation on aarch64
(`ets_split.erl`, microseconds, OTP 29 for reference):

| operation | before | after | OTP 29 |
|---|---:|---:|---:|
| insert only (baseline) | 7,791 | 8,047 | 4,826 |
| `+ match` with a bound key | 42,021 | 14,142 | 6,765 |
| `+ match_delete` | 31,531 | 11,985 | 6,323 |
| `+ match` with a free key | 67,824 | 56,809 | 20,585 |
| the whole micro | 88,132 | **44,173** | 23,135 |

3.81x -> 1.91x of OTP. Three changes: `ets:info/2` became a NIF over fields the
table already holds (it supported only `size`, and computed it as
`length(tab2list(T))`), which is where `keypos` comes from; `select/2` and
`select_delete/2` narrow to a `lookup/2` when the single clause's head is a
tuple with a ground key element; and `ms_variable/1` and `ms_variable_number/1`
stopped calling `atom_to_list/1` -- once per atom of the pattern per object
traversed -- for the `'$1'..'$9'` that cover essentially every match spec.

`tab2list` itself was never the problem: it is 1.9x *faster* than OTP's. What
remains is the per-object map bookkeeping in the Erlang match-spec
interpreter, which wants the pattern compiled once per call.

## Two things the previous report got wrong

**Code volume.** It claimed arm32 emits about a quarter more instructions than
aarch64 for the same module. Those precompiles came from `libs/jit/_build`, a
rebar build of the JIT compiler last refreshed on 25 July, not from the tree
being measured. With the compiler the build actually uses, and the label jump
table excluded (8 bytes per label on arm32 against 4 on aarch64, which is not
code), arm32 emits **12-15% fewer** instruction words. Corrected in
`b13bfd504`. The cost was never volume: disassembling `local1/1` for both
backends gives 27 instructions against 25, but six of arm32's fed a dependent
instruction straight from memory, on an in-order core with a 3-cycle load-use
penalty. That is what this round removed.

**Loop residency is not an item.** `supports_loop_residency/0` only controls
whether the frontend shares the `op_call_last` block through the tail cache;
the residency itself is the backend keeping x0-x3 in home registers across a
loop. arm32 has no home registers, so there is nothing to keep resident and
enabling the capability would only make the code bigger. The real item behind
that name is x-register homes, below.

**The ESTONE bimodality is the board, not the VM.** Solved, and the previous
report was wrong about it twice over.

- Not code placement: eight runs with ASLR and eight under `setarch -R` give
  spreads of 1.076 and 1.094. Deterministic mmap addresses do not move it, so
  the cache-set-aliasing hypothesis is dead.
- Not SMP or core placement: `taskset -c 0`, `-c 0-1` and the default all give
  the same 37.6k-49.9k spread. (One core also scores the same as four --
  ESTONE on this host is effectively single-threaded.)
- It is **hardware throttling to 600 MHz that the cpufreq driver does not
  report**. `scaling_cur_freq` reads a constant 900,000 through every run, but
  sampling `vcgencmd measure_clock arm` once a second shows the ARM clock at
  600 MHz for 4-10 seconds of each ~24-second run. `vcgencmd get_throttled` is
  `0x50005`: currently under-voltage and currently throttled. 900/600 is
  exactly the ~1.5x by which the affected micros bifurcate.

That also explains why it looked like four specific micros: they are
`large_local_dataset_work`, `alloc`, `bif_dispatch` and `binary_h`, which are
four **consecutive** entries in the middle of the suite, i.e. a time window
rather than a property of the code. And it is not AtomVM-specific -- the
previous report claimed GRiSP varied by "well under 1%", but its own worst
round in this session inflates the same four micros by the same factor
(alloc 107,187 against 65,000, bif_dispatch 573,940 against 380,000,
binary_h 1,959,618 against 1,250,000).

Consequences: interleaved comparisons stay valid, since the throttling hits
every VM in the round equally. Per-micro medians over a handful of rounds do
not, for those four. And there is no ~5% of ESTONE to be won by aligning hot
JIT code, as the previous report suggested -- that win does not exist. Fixing
the Pi's power supply would make the bench quieter; nothing in AtomVM will.

## What is left, in order

1. **x-register home registers on arm32.** Every block still opens with
   `ldr r6, [r7, #44]` to read x0, where aarch64 spends a `mov` from its home.
   This is the largest remaining item and the reason "loop residency" appeared
   on the old list. It needs a register: r11 is now the reduction count, and
   r12 is already the spill temp in three places (`?IP_REG`), so this is a
   register-allocation problem before it is a codegen one.
2. **Make the reduction flush conditional.** The 2-10% given back on
   primitive-heavy micros is one `str` per tail-called primitive, emitted
   unconditionally as aarch64 does. Primitives that cannot reschedule do not
   need it, and `jit_prim_pure.hrl` already classifies them.
3. **Compile the ets match spec once per call** instead of re-walking the
   pattern per object; that is the rest of the free-key traversal.
4. **The same reduction pinning on the other backends.** Only aarch64 and now
   arm32 pin it; riscv32, riscv64, xtensa, armv6m and x86_64 all still go
   through memory, and RISC-V has callee-saved registers to spare.
5. ~~The bimodality~~ -- solved above, and it is the board's power supply, not
   anything in AtomVM.

## Method notes

- `tools/dev/fcalls_bench.erl` splits ESTONE's `fcalls` into its six call
  shapes; [`ets_split.erl`](ets_split.erl) splits the `ets` micro by operation.
- Always check the per-round spread before believing a per-micro median on this
  host: the four micros the throttling window lands on swing ~50%, and five
  rounds is not enough to average that out. `fcalls` and `ets` are stable
  (spread 1.01-1.11) and can be read directly. `scaling_cur_freq` will not warn
  you -- sample `vcgencmd measure_clock arm` instead.
- Precompiling a 260-module OTP corpus for both backends is the cheap
  regression check: the aarch64 output is byte-identical across all 260, and
  arm32 grows 0.35% (the flush is on cold error tails; the savings are on hot
  paths).
