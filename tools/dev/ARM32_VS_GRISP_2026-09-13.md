# arm32: what carries over, and where GRiSP's JIT stands — 2026-09-13

Host: Raspberry Pi 2 (`mx2.local`), armv7l, 4 cores, 920 MB, Raspbian 13,
GCC 14.2. AtomVM builds are Release with the JIT enabled
(`-DAVM_DISABLE_JIT=OFF -DAVM_PRECOMPILED_TARGETS=arm32`). Every VM runs the
same OTP 29-compiled ESTONE beams, loaded as plain BEAM and compiled by the
respective JIT at load time.

## The AArch64 work being carried over

The parallel session's uncommitted work on `w30/jit-edge` is five changes, all
measured on AArch64:

| change | where | AArch64 effect |
|---|---|---|
| `select_val` integer ranges | `jit.erl` codegen | ESTONE 1.069, pattern micro +14.2% |
| Leaf NIF direct dispatch | `jit.c`, `nifs.c`, `exportedfunction.h` | ESTONE 1.0219, BIF dispatch +27.6% |
| Direct `get/1` dictionary lookup | `bif.c` | ESTONE 1.0059, BIF dispatch +9.8% |
| Comparison frame split (NOINLINE) | `term.c`, `term_hash.c` | unicode_util 1.0142, erl_parse 1.0120 |
| Hash-ordered `maps:from_list` | `nifs.c`, `termmap_champ.c` | part of the from-list pass |

It does **not** include the atom rank work: `atom_table.c` on that branch is
untouched, `sort_key` and the byte-prefix comparison are still there, and the
JIT compare stubs still read `HNode->sort_key`. The rank branch
(`w30/atom-rank`, `de513305e`) remains separate and unmerged.

Four of the five are plain C and apply to every backend unchanged. The
`select_val` range work is JIT codegen, and it was gated behind
`supports_select_val_binary_search/0`, which only AArch64 and x86-64 export —
so on arm32 it did nothing at all.

## Porting the select_val ranges to arm32

`op_select_val_int_ranges/5` needs only a subtract, an unsigned bound compare
and a tag check; nothing about it requires a jump table. The gate is now a
separate capability, `supports_select_val_ranges/0`, exported by the three
backends that implement the `'(uint)>'` condition (AArch64, arm32, x86-64);
the jump-table/binary-search dispatcher keeps its own gate. armv6m, riscv32,
riscv64, xtensa and wasm32 have no unsigned-compare condition and are
unchanged — trying it there fails in `if_block_cond` immediately, which is how
the missing condition was found.

Evidence the port is inert where it should be and live where it should be:
precompiling the 156 OTP 29 stdlib + compiler modules that the JIT accepts
(zstd.beam uses opcode 149, unimplemented, in both) gives **156/156
byte-identical** output for `aarch64`, and **7 of 156 differ** for `arm32`.
`estone_test.beam` is one of the modules that changes: its arm32 native code
shrinks from 107,004 to 106,620 bytes. The pattern micro is exactly the shape
the pass targets — `pat_loop1/2` matches list element four against 0, 1, 2, 3,
four consecutive values sharing three targets.

The 3170 JIT unit tests pass, and so does the full Erlang suite run on the
board itself.

## arm32 backend feature gap

Capabilities AArch64 exports that arm32 does not, in rough order of what the
AArch64 measurements suggest they are worth:

| capability | what it buys |
|---|---|
| `supports_select_val_binary_search` | O(1) jump table for dense integer selects (ported partially: ranges now, table still missing) |
| `set_branch_hints` / `rewind_stream` / `take_overflows` | optimistic short-branch emission with backtrack |
| `return_cross_module` | inline cross-module return instead of a primitive call |
| `get_list_head_tail` | fused head+tail load (ARM has `ldrd`) |
| `supports_inline_tuple2_eq` | inline two-element tuple equality |


## ESTONE: the AtomVM A/B/C

Nine alternating rounds, one warmup, `performance` governor at 900 MHz, nothing
else on the box. `base` is `w30/jit-edge` at 800058359, `cand` adds the parallel
session's five changes, `cand2` adds the arm32 range port.

| | base | cand | cand2 |
|---|---:|---:|---:|
| ESTONE median | 45,197 | 48,708 (1.078) | 49,397 (1.093) |

Those totals overstate the gain, because four micros on this host are
**bimodal**: `alloc`, `bif_dispatch`, `binary_h` and `large_local_dataset_work`
each land in one of two clusters about 50% apart, together, chosen once per run
and identically distributed across all three builds. For example `alloc` is
either ~1,600 or ~2,400 in every build, and `bif_dispatch` in `base` is either
~2,900 or ~4,300. A median over nine rounds inherits whichever cluster happened
to win the coin toss more often. Comparing within clusters:

| | base | cand | cand2 |
|---|---:|---:|---:|
| low-cluster median | 44,906 | 45,569 (1.015) | 46,134 (1.027) |
| high-cluster median | 47,964 | 49,035 (1.022) | 49,596 (1.034) |

So the honest reading on arm32 is about **+2% for the parallel session's work
and another ~+1.2% for the range port**, not +9%.

The individual effects are much clearer than the totals:

- `bif_dispatch` moves **+35% in the low cluster and +38% in the high one**
  (2,890→3,977 and 4,341→5,981). The leaf-NIF path pays on arm32 as it does on
  AArch64; it just does not move the ESTONE total much here.
- `pattern` is not bimodal and separates cleanly: every `cand` round is between
  20,378 and 20,554, every `cand2` round between 20,918 and 21,191 — the range
  port is worth **+2.4%** on that micro, with no overlap. That is well short of
  the +14% AArch64 saw, because arm32's baseline was a short linear compare
  chain rather than a jump table, but it is real and free.
- everything else (`alloc`, `binary_h`, `large_local_dataset_work`, `lists`,
  `trav`, `fcalls`, `msgp*`) is unchanged within cluster.

The bimodality itself is worth chasing: it appears only in AtomVM (OTP 29 and
GRiSP rounds vary by well under 1%), it switches four micros at once, and the
Cortex-A7 has a 32 KB **2-way** L1I. Runtime-JIT code landing at a different
mmap offset from run to run is the obvious suspect — cache-set aliasing of a hot
loop would look exactly like this. If that is what it is, aligning hot JIT code
would win ~5% of ESTONE on this class of core, for free and independently of
everything above.

## erlc: AtomVM, OTP 29, and GRiSP's JIT

Thirteen OTP 29 sources from stdlib and kernel, three interleaved rounds, per-file
medians summed. All three compilers run **the same OTP 29 compiler code**: the
AtomVM binaries pack OTP 29's `compiler` and `stdlib` beams, precompiled to arm32
native by `jit_precompile` (`build_erlc_variant.sh aot`, `TARGET=arm32`).

| compiler | total (ms) | vs AtomVM |
|---|---:|---:|
| AtomVM AOT (cand2) | 42,616 | 1.00 |
| AtomVM AOT (base) | 42,982 | 0.99 |
| OTP 29 erlc (no JIT) | 57,287 | **0.74** |
| GRiSP OTP 29 erlc (arm32 JIT) | 76,962 | **0.55** |

AtomVM is **1.34x** OTP 29's own erlc and **1.81x** GRiSP's. GRiSP's JIT is
**0.74x its own interpreter** on this workload: BeamAsm compiles every module it
loads, and erlc is a short-lived process that loads the whole compiler each time.
The floor shows it — `dets_sup.erl`, a 1.3 KB module, takes 172 ms on AtomVM,
1,445 ms on OTP 29 and 3,717 ms on GRiSP. The one file where GRiSP wins is
`erl_scan.erl` (15,220 ms against our 17,925 and OTP 29's 18,184), the longest
single compile in the set, where its load-time compilation finally amortises.

## Can the GRiSP JIT run the compiler?

Yes, now. Their OTP 27 branch could not: building it aborts in `parsetools` with
`size_object: bad tag for 0x0` while its freshly built `beam.jit` compiles
`leex.beam`. The OTP 29 branch (`arm32-jit/OTP-29.0.6`, `e649d63`) builds the
**entire OTP library tree with itself** — asn1, compiler, stdlib, ssl, mnesia,
snmp, dialyzer, the lot — with no abort, and then compiles all 13 benchmark
files. `Erlang/OTP 29 [erts-17.0.6] [source] [32-bit] [smp:4:4] [jit]`.

One caveat about *their* branch, not the JIT: it does not compile on armv7 with
GCC 14 as shipped. `loc_index_to_cover_id` is `unsigned int *` in
`erts/emulator/beam/jit/load.h`, `Uint32 *` (i.e. `unsigned long *` on 32-bit) in
`beam_code.h`, and is read into a `const unsigned *` in `erl_bif_coverage.c`;
two of the three have to be corrected before `make` gets through the emulator.

same machine, same session (a separate five-round session also included OTP 29
without a JIT: 23,427).

| float_arith | 369 | 607 | 0.61 |

| ets | 228 | 940 | **0.24** |

Message passing is the one thing we are decisively better at, by more than
double — the shallow-copy and link/monitor work shows up here. The losses
cluster into three groups: raw call overhead (`fcalls` 0.45, and `links` at 0.39
is mostly spawn plus link), 32-bit arithmetic (`int_arith` 0.57, `float_arith`
0.61), and list/tuple traversal (`lists`, `trav`, both dataset micros). `ets` at
0.24 is a library-implementation gap, not a JIT one.

`fcalls` is the single biggest lever and maps directly onto the missing arm32
capabilities: `return_cross_module` (we call a primitive where AArch64 returns
inline) and the branch-hint/backtrack machinery. `lists`/`trav` map onto
`get_list_head_tail`. None of that is speculative work — it is all implemented
on AArch64 already and simply never ported.

Note: the fifteen-round session recorded `throttled=0x50005`, i.e. the board
took an under-voltage dip during it (48 °C, so not thermal). All three VMs
interleave, so the comparison stands, and a separate un-throttled five-round
session gives the same picture (GRiSP 63,752, AtomVM 45,795–50,079).

## What to do next on arm32

1. Port `return_cross_module` and `get_list_head_tail`; they are the two
   capabilities that map onto the two worst micro groups, and both already exist
   on AArch64.
2. Investigate the four-micro bimodality. If it is JIT code placement against the
   A7's 2-way L1I, aligning hot code is worth about as much as everything
   measured here put together.
3. The jump-table half of `select_val` (the part still gated on
   `supports_select_val_binary_search`) for arm32.
4. `ets` at 0.24 is the largest single ratio in the table and has nothing to do
   with the JIT.

## Where the arm32 gap actually is — measured on both word sizes, 2026-09-13 (evening)

The question this section answers: is the arm32 deficit code generation, and
which part of it is *not* arm32's fault at all? The method is to measure the
same ESTONE micros on both machines against the best BEAM available there, and
look at which ratios move. Anything that is equally bad on AArch64 is a library
or runtime gap; only what degrades on arm32 can be the backend.

- AArch64: this Mac, AtomVM `w30/jit-edge` head (Release, JIT) against
  `/opt/local` OTP 29 with BeamAsm. Seven interleaved rounds, per-micro medians.
  **ESTONE 2,547,231 vs 2,583,228 — 0.986x, parity.**
- arm32: `mx2.local`, `~/avm-head/build.rel` against GRiSP `arm32-jit/OTP-29.0.6`
  and stock OTP 29 without a JIT. Three interleaved rounds.
  **ESTONE 46,307 vs 64,281 vs 20,529 — 0.72x of GRiSP, 2.26x of the interpreter.**

Both columns are AtomVM time divided by BEAM time, so **below 1 means AtomVM
wins**; `swing` is how much worse the ratio gets when the same micro moves from
AArch64 to arm32.

| micro | AArch64 AVM/BeamAsm | arm32 AVM/GRiSP | swing |
|---|---:|---:|---:|
| fcalls | 0.50 | 2.24 | **4.51** |
| large_local_dataset_work | 1.05 | 2.69 | **2.56** |
| lists | 0.80 | 1.82 | **2.29** |
| large_dataset_work | 0.95 | 1.70 | 1.79 |
| trav | 0.86 | 1.46 | 1.71 |
| float_arith | 1.14 | 1.64 | 1.45 |
| bif_dispatch | 1.00 | 1.31 | 1.30 |
| binary_h | 1.24 | 1.61 | 1.30 |
| alloc | 0.95 | 1.17 | 1.23 |
| pattern | 1.04 | 1.20 | 1.15 |
| int_arith | 1.59 | 1.77 | 1.11 |
| ets | 3.97 | 4.16 | 1.05 |
| timer | 1.03 | 0.96 | 0.94 |
| generic | 0.84 | 0.78 | 0.93 |
| links | 2.83 | 2.61 | 0.92 |
| msgp_huge | 0.76 | 0.55 | 0.73 |
| msgp_medium | 2.34 | 0.43 | 0.18 |
| msgp | 2.35 | 0.42 | 0.18 |

Three groups fall out of that table:

**Not arm32 at all.** `ets` is 4x on both machines and `links` is ~2.7x on both.
Those are library and runtime gaps that the arm32 report previously listed as
arm32 losses; they are nothing of the kind. `int_arith` is already 1.59x on
AArch64, so only a tenth of its arm32 loss is the backend. Fixing `ets` helps
every target at once, and it is the single largest per-micro ratio we have.

**Not code generation either — the scheduler, and it flips with the machine.**
`msgp`/`msgp_medium` are 2.34x *against* us on the Mac and 0.42x *for* us on the
Pi. Same code, opposite verdict: on four slow in-order cores our message path
wins by more than double, on a wide many-core machine BEAM's scheduler wins by
the same margin. Treat any msgp movement as a statement about the host.

**Code generation, and it is mostly one path.** `fcalls` swings 4.5x, and
breaking it into its six call shapes (`fcalls_bench`, 882 x 400 calls each,
interleaved) says precisely which:

| shape | AArch64 AVM | AArch64 BeamAsm | ratio | arm32 AVM | arm32 GRiSP | ratio |
|---|---:|---:|---:|---:|---:|---:|
| local0 (local tail) | 174 | 267 | 0.65 | 5,775 | 9,738 | **0.59** |
| remote0 (external tail) | 381 | 276 | 1.38 | 18,838 | 17,934 | 1.05 |
| app0 (apply tail) | 339 | 268 | 1.26 | 18,722 | 18,467 | 1.01 |
| local1 (local non-tail) | 467 | 1,718 | 0.27 | 24,699 | 15,815 | 1.56 |
| remote1 (external non-tail) | 705 | 1,647 | 0.43 | 38,592 | 17,585 | 2.19 |
| app1 (apply non-tail) | 776 | 1,727 | 0.45 | 38,163 | 18,275 | 2.09 |
| all | 2,713 | 5,706 | 0.48 | 144,599 | 99,560 | 1.45 |

Times in microseconds. **Tail calls on arm32 are fine** — we beat GRiSP on
`local0` and tie on the two external tail shapes, exactly as on AArch64. The
entire `fcalls` loss is the **non-tail call and its return**, where AArch64 is
2.2-3.7x faster than BeamAsm and arm32 is 1.6-2.2x slower. Per call, in cycles:
AtomVM spends ~5 on AArch64 and ~42-63 on arm32 for `local1`; BeamAsm spends
~20 and ~27-40. Their arm32 backend costs them 1.4-2x over their AArch64 one;
ours costs us 8-12x.

Two mechanisms, one structural and one missing work:

1. **The cp is two words on 32-bit.** `op_return_same_module/2` in `jit.erl`
   branches on `MMod:word_size()`: at 8 the cp packs `(module_index << 24) |
   (offset << 2)` into one word, so a return is one load, a shift and a compare;
   at 4 it is `?CP_MODULE` plus `?CP_OFFSET`, so both the call (`set_cp/1`,
   two stores plus an ADRL pair to materialise the resume address) and the
   return (`return_to_cp_address/1`, seven instructions) pay double. Every
   32-bit backend pays this, not just arm32.
2. **Fifteen capabilities AArch64 exports that arm32 does not**, found by
   grepping every `erlang:function_exported(MMod, ...)` probe in the JIT
   frontend: `return_cross_module`, `get_cp_base`, `call_fun_with_cp_direct`,
   `get_list_head_tail`, `jump_table_dispatch`, `supports_inline_tuple2_eq`,
   `set_branch_hints`/`rewind_stream`/`take_overflows`, `compare_stub_call`,
   `map_get_stub_call`, `move_imported_gcbif_to_native_register`,
   `shift_right_arith_reg`, `load_be_unsigned`/`store_be`,
   `add_deferred_raise`/`take_deferred_raises`, `read_shrink_probe_mismatch`;
   plus `supports_loop_residency/0` returning **false**. `get_list_head_tail`
   (ARM has `ldrd`) maps onto `lists`/`trav`/both dataset micros, which are the
   next three largest swings after `fcalls`.

The volume shows up in the output. Both A32 and AArch64 are fixed 4-byte
instructions, so the native chunks are directly comparable; precompiling the
same OTP 29 beams for both gives:

| module | AArch64 words | arm32 words | arm32/AArch64 |
|---|---:|---:|---:|
| erl_scan | 71,710 | 87,871 | 1.23 |
| lists | 57,073 | 69,685 | 1.22 |
| estone_test | 21,144 | 26,413 | 1.25 |
| dict | 13,803 | 17,629 | 1.28 |
| maps | 12,768 | 16,329 | 1.28 |
| gb_trees | 11,052 | 14,102 | 1.28 |
| ordsets | 2,405 | 3,314 | 1.38 |

A quarter more instructions for the same source, on a dual-issue in-order core.

| inet_tcp_dist.erl | 1,684 | 3,007 | 5,089 | 0.56 | 0.33 |

**`erl_scan.erl` is the only file GRiSP compiles faster than we do** (1.18x);
`global.erl` is a tie. Those are also the only two files long enough for
BeamAsm's load-time compilation of the whole compiler to amortise.

That is what the 1.81x total is hiding. The smallest module in the set costs
172 ms on AtomVM, 1,445 ms on OTP 29 and 3,717 ms on GRiSP, which is close to a
pure per-launch cost. Subtracting it:

| | fixed/launch | steady-state total | AVM ratio |
|---|---:|---:|---:|
| AtomVM AOT | ~172 ms | 40,380 ms | 1.00 |
| OTP 29, no JIT | ~1,445 ms | 39,100 ms | 1.03 |
| GRiSP OTP 29 JIT | ~3,717 ms | 28,900 ms | **1.40** |

So on compile work itself we are about **1.4x slower than GRiSP's arm32 JIT**
and level with the arm32 interpreter — which agrees with ESTONE's 1.38x from a
completely different workload. Our erlc win on this board is real and it is
worth having, but it is a startup win, not a code-generation win. The two long
files measure the same thing per-file: 1.54x and 1.52x once the launch cost
comes off.

## Revised priority list

1. **Non-tail calls on 32-bit.** Biggest swing by a factor of two, and the
   32-bit two-word cp means the fix helps riscv32, xtensa and the Thumb
   backends as well, not only arm32.
2. **`get_list_head_tail` on arm32** (`ldrd`): `lists`, `trav` and both dataset
   micros are the next three swings.
3. **`ets`**, which is 4x on *both* word sizes and has nothing to do with the
   JIT. Previously mis-filed as an arm32 problem.
4. `supports_loop_residency` and the branch-hint/backtrack trio for arm32.
5. The four-micro bimodality, still unexplained and still worth ~5% here; the
   `fcalls_bench` runs show it too (round 1 is 1.52x round 2 on every shape,
   while GRiSP varies by under 2.5%).
