# Where aarch64 code size is still going, and what it would cost to get it

Follow-on from BULK_MOVES. Measured over the 260-module corpus (8,224,375
instructions of aarch64) and over the JIT compiler's own 27 modules.

## The metric matters more than I realised

`tools/dev/jit_compiler_size.sh` measures the native size of the JIT compiler's
own modules. It is sharper than a corpus measurement because the compiler
contains *every* backend, so it charges a change for the code it adds as well as
crediting it for the code it saves. Session to date:

    aarch64 -1.47%   arm32  -0.68%   armv6m  -0.25%
    riscv32 +0.79%   riscv64 +0.80%  x86_64  +0.83%
    xtensa  +0.90%   wasm32  +1.07%

The four backends that gained nothing from this work got **bigger**, by up to
1.07%, because they still have to carry the frontend paths and the aarch64 and
arm32 backend code that grew. The corpus measurement reported every one of them
as "+0.00%, byte-identical" and hid this completely.

Both numbers are real, they just answer different questions: corpus size is the
quality of the generated code, compiler size is that *plus* the compiler's own
footprint. For a target that ships the JIT on-device the second is the one that
matters.

## Branch ranges: 16227 instructions of pure waste

    forward conditional branches            348488
    branch-over-b trampolines                46367   (0.56% of all instructions)
      target within b.cond reach (16K-1M)    30140
      target within the branch's OWN reach    16227

A trampoline is `tbnz +1 ; b <target>`: a conditional branch that skips over an
unconditional one, used when the target is out of the conditional branch's
reach. **16227 of them have a target the conditional branch could have reached
directly.** Those are a wasted instruction *and* a wasted branch each.

It is not a missing capability: every stream module exports `committed_offset/1`,
so `backtrack_enabled` is true and `fuse_cond_branch_forward` does try the
single-branch form for forward branches. These are the cases where it gives up --
the label resolves after the stream has committed past the branch, and a
committed instruction cannot be rewritten.

The fix is the standard assembler technique: a **branch relaxation pass** over
the finished buffer, shrinking branches and recomputing offsets to a fixpoint.
It recovers those 16227 and would likely find more, since shrinking one branch
brings other targets into range. **This is the one item here with no speed cost
at all -- it removes a branch, so it is a small gain.** Recommended.

The other 30140 are genuine: the target really is beyond `tbz`'s +/-32KB. They
could become a single `b.cond` (+/-1MB reach), but only by first putting the
condition in the flags with a `tst`, which is the same two instructions. Worth
noting these are largely a consequence of the cold-arm outlining, which moved
fallbacks to the module tail and out of reach.

## Factorisation: the call boilerplate, and why it is not free

Repeated exact sequences, jump tables excluded (their entries all differ; they
only looked identical because the analysis normalises branch targets away):

    56629x  saves 169882 (2.08%)  str x22,[x21,#24] | str x23,[x21,#80] | blr x16 | ldr x30,[x19,#48]
    50255x  saves 150760 (1.84%)  ldr x22 | ldr x23 | ldp x25,x26 | ldp x27,x28
    30078x  saves 150383 (1.84%)  str x7,[x19,#8] | ldr x7,[x20,#16] | str x22 | str x23 | str w24 | br x7
    19173x  saves 134202 (1.64%)  subs x24,#1 | b.ne | adr | ... | br x7

Every one is the C-call boilerplate: spill hp and e, call, reload the link
register, reload hp, e and the four x-register homes. Around 8 instructions
surround each of ~50000 primitive call sites -- roughly 5% of all code.

Outlining it into shared stubs would save about 2% each, but it is **not** free:

  - It adds a `bl` and a `ret` to the hottest path in the VM. A primitive call
    already costs an indirect `blr`; adding two well-predicted branches is
    perhaps 2-4 cycles against a call that costs tens. That is a small relative
    cost but it is on *every* primitive call, and "small" here needs measuring,
    not assuming.
  - `x30` is awkward. Generated code does not use it as a link register: it
    reloads it from `jit_state->dispatcher_ret` after every call. A `bl` to a
    stub would clobber the value that reload just produced, so the reload has to
    move out of the stub and the sequencing has to be reworked.

So: real, large, and a genuine size/speed trade rather than a free win. It
should be measured on the hot path before it is built, and it is the opposite
of "no noticeable speed cost" until that measurement says otherwise.

## Recommended order

1. Branch relaxation pass -- 16227 instructions, no speed cost, small gain.
2. Nothing else here is free. The factorisation is worth prototyping only with a
   hot-path A/B attached to it.

## Chasing the remaining bcc trampolines (2026-09-15)

After commit 4d9092934 the corpus has 8862 `b.cond` trampolines left, and 8861
of them still have a target inside bcc's +/-1MB. Tracing where they come from
took four wrong guesses, each cheap to disprove:

  - `fused_branch_bytes`' out-of-reach fallback: hooked it, and every hit is a
    `tbz`/`tbnz` with a distance of 33136 to 265652 -- beyond `tb`'s +/-32KB but
    inside bcc's. Those are legitimate and account for the 26587 remaining *tb*
    trampolines, not the bcc ones.
  - Frontend `if_block` sites whose body is a single `jump_to_label`: there are
    two in the whole file, one of which is the fallback that aarch64 never takes.
  - The `{'and', _}` compound-condition fallback in `jump_to_label_cond`: 36 in
    all of `lists`.
  - The far clause of `call_only_or_schedule_next`: instrumented it, and on
    `beam_ssa_codegen` the split is 382 direct, 846 unknown, 0 far -- the path
    fixed in 4d9092934 is being taken.

Hooking `jit_aarch64_asm:bcc/2` for every emission with an offset of exactly 8,
with a caller stack trace, found it: **`if_else_block` when the true arm emits
nothing.**

    b.cond +8          <- skip to the else arm when the condition is false
    b <end>            <- true arm is empty, so this is all it does
    <else arm>
    end:

424 of them in `beam_ssa_codegen` alone. It is semantically
`if not Cond -> ElseArm end`, so the whole thing is one inverted conditional
branch over the else arm, and the `b` is pure waste.

### Why this one is not a two-line fix

The saving only exists if the `b` is never emitted, and whether the single
branch can reach depends on the size of the else arm, which is not known until
after it has been emitted. Reserving 8 bytes and writing `b.cond <end>` + `nop`
keeps the instruction count but saves no space, which is the whole point here.

The clean way is the mechanism forward branches already use: take a branch id,
reserve 4 bytes optimistically, emit the else arm, and then either patch the
single inverted branch or -- if the distance does not fit -- record an overflow
so the next pass reserves 8 and emits the pair. `emit_finalize_loop` already
re-emits on overflow, and the `branch_counter`/`overflows`/`branch_hints` state
is already threaded through. It is contained, but it is a change to a core
control-flow primitive that every backend's frontend leans on, so it wants its
own measurement and test pass rather than being tacked onto this one.

Estimated worth: most of the 8862, so roughly another 0.1% of aarch64 corpus
size, on the same no-speed-cost footing as 4d9092934 (it removes a branch).

## Condition fusion: what still feeds a b.cond (2026-09-15)

Two-instruction sequences feeding a conditional branch, over 8189276 corpus
instructions:

    33787  and x16, x7, #0x3f | cmp x16, #0xb     boxed subtag test
    31712  ldr x7, [x23]      | cmp x7, #0x3b     load then compare to NIL
    20098  lsr x8, x8, #6     | cmp x8, #0x2      arity from a header
    19553  sub x7, x23, x22   | cmp x7, #0x17     heap room
    15192  mov x7, x25        | cmp x7, #0x8b     *the copy is dead*
    13158  orr x8, x8, x7, asr #63 | cmp x8, #0x0

Most of these cannot fuse further: aarch64 has no flag-setting `orr`, and
`(x band Mask) == Value` genuinely needs both an `and` and a `cmp` unless Value
is zero. Two can:

  - **`cmp Rn, #0` then a conditional branch is `cbz`/`cbnz`.** 13060 sites use
    an unsigned condition after `cmp #0` (`b.ls` after `cmp #0` is "== 0",
    `b.hi` is "/= 0") plus 133 direct eq/ne. **~13193 instructions**, and it
    shortens the dependency chain rather than just the instruction count.
  - **`mov Rd, Rs` immediately before `cmp Rd, ...` leaves the copy dead** --
    `cmp` does not write its first operand, so compare `Rs` directly. **10220
    sites**, nearly all `mov x7, x25` where x25 is an x0 home. This is the same
    class as the `can_test_in_place` work already shipped; some path is still
    materialising a home into a scratch before building the condition.

Neither is specific to aarch64 in principle: every backend has a
compare-against-zero branch form, and the dead-copy one is a frontend
materialisation that all backends pay.

## Factorising the unlikely paths

**22.9% of all generated code** sits in a block that is skipped by a forward
conditional branch and contains a call -- 81423 such blocks, median 47
instructions. These are the inline slow paths: bignum arithmetic, error raises,
anything that leaves the fast path.

Grouping them by shape (branch targets normalised away) gives 32427 distinct
shapes over 81423 instances, and outlining every shape that repeats and pays
for itself would save **1307322 instructions, 15.96% of all code**. The top
three shapes are each emitted at exactly 3055 sites:

    3055x  51 instrs   and x9, x8, #0x3 | cmp x9, #0x3 | b.eq ...
    3055x  47 instrs   and x9, x7, #0x3 | cmp x9, #0x3 | b.eq ...
    3055x  42 instrs   tbnz | tbnz | and x9, x8, #0xfffffffffffffffc ...

`and #3; cmp #3` is the small-integer tag test, so these are the not-a-small-int
fallbacks -- exactly the "big integers" case.

This is by far the largest size opportunity found in this session, and unlike
the call-boilerplate factorisation the `bl`/`ret` lands on a path that by
construction rarely executes, so it does not have the hot-path cost that made
that idea unattractive.

**Two caveats on the 15.96%, both of which lower it:**

  1. The shapes were compared with branch targets normalised away. Blocks that
     differ only in where they branch *out* to are counted as identical here but
     are not directly shareable. Internal branches are fine (relative), and the
     return is what `ret` is for, but an exit to a per-site error label is not.
     The true figure needs the same census with external targets kept.
  2. Sharing needs the sites to agree on register state at entry and exit.
     Byte-identical bodies are strong evidence they already do -- that is why
     this is more promising than the general call-boilerplate case -- but it is
     evidence, not proof, and the deferred-raise outlining currently sidesteps
     the question entirely by never returning.

`x30` also needs handling: generated code reloads it from
`jit_state->dispatcher_ret` after every call, so a stub entered with `bl` must
preserve the return address across the inner call before its `ret`. That is two
instructions in the stub, paid once.

### The census with external targets kept (2026-09-15)

Run three ways over the same 81423 blocks:

    external targets normalised away        15.96% savings   (the first figure)
    external targets rejected outright       0.16%
    identical external targets still match   0.17%

**The opportunity is 0.17%, not 15.96%.** 78766 distinct shapes over 81423
instances: almost every block is unique, and it is unique *because of where it
branches out to*, not because of its body. Only 3591 blocks have no per-site
external reference at all; most have between one and five.

What those external references are:

    137058  b          unconditional exit
     53140  b.ne       conditional exit
     39383  cbz
     16078  tbz
      4535  b.eq
     40191  adr        the per-site continuation address

So roughly 250000 of them are **branches to per-site labels** and only 40191 are
an `adr` of a value. Parameterising a value is easy -- pass it in a register.
Parameterising a branch target means the shared stub exits through a register
the caller loaded, so a block with five external branches needs five `adr`s and
a `bl` at each site: six instructions where the inline block was 47. That still
pays arithmetically, but it is a real calling convention with real register
pressure at the call site, not a peephole.

Confirming the diagnosis: parameterising *every* external reference brings the
saving back to 15.95%. The entire opportunity lives in the control flow, and
none of it in the block bodies.

### What this leaves

Two separable ideas, and the measurement only kills one of them:

  - **Sharing** identical cold blocks: 0.17% as things stand. Not worth a
    calling convention.
  - **Relocating** cold blocks to the module tail: no size change at all --
    the same instructions, moved -- but it densifies the hot path, which is the
    locality argument. The mechanism already exists (`cond_raise_outlined` does
    exactly this for raises) and could be pointed at the bignum fallbacks. Its
    benefit is an icache effect that static analysis cannot size; it has to be
    built and benchmarked.

The 3055-site bignum fallbacks are still the obvious first target for the
second idea, because they are large (42 to 51 instructions) and, being the
not-a-small-int arm, genuinely cold.
